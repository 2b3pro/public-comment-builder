Analyze the following federal regulatory docket and generate a citizen-facing analysis that enables the drafting of substantive, legally meaningful public comments.

CURRENT DATE: {{currentDate}}

DOCKET TEXT:
{{docketText}}

OBJECTIVE:
Produce structured, plain-language intelligence that helps ordinary citizens submit comments agencies must meaningfully consider under the Administrative Procedure Act.

OPERATING PREMISE (Federal Reality Check):
• Comments that merely express support or opposition carry little weight.
• Agencies must respond to significant, relevant, evidence-based comments.
• The strongest comments explain *how* the proposal affects real people, assumptions, markets, or systems—often through lived experience or concrete examples.

════════════════════════════════════════════════════════════════════
STEP 1: DETECT THE NOTICE TYPE (CRITICAL)
════════════════════════════════════════════════════════════════════

Before generating any analysis, determine what type of federal notice this is. The notice type determines what kind of response framework is appropriate.

NOTICE TYPE DETECTION RULES:

1. **proposed_rule** - A Notice of Proposed Rulemaking (NPRM)
   - Look for: "proposed rule", "proposed regulation", "rulemaking", regulatory text with section numbers
   - Citizens can express support, opposition, or conditional positions
   - Response framework: Support / Oppose / Mixed positions with reason cards

2. **pra_notice** - Paperwork Reduction Act Information Collection Request
   - Look for: "Paperwork Reduction Act", "PRA", "OMB Control Number", "information collection", "burden estimate", "burden hours"
   - Citizens cannot simply "support" or "oppose" - they must address PRA factors
   - Response framework: PRA factors (necessity, burden accuracy, quality, burden minimization)

3. **rfi** - Request for Information or Advance Notice of Proposed Rulemaking (ANPRM)
   - Look for: "request for information", "RFI", "seeking comment on", "advance notice", "ANPRM", numbered questions the agency wants answered
   - Citizens should respond to the specific questions posed
   - Response framework: Question-based response cards

4. **general** - Other notices (final rules, guidance, announcements)
   - When it doesn't fit the above categories
   - Response framework: Issue-based response cards

Set `noticeType` to one of: "proposed_rule", "pra_notice", "rfi", "general"

STEP 2: PLAIN-LANGUAGE ORIENTATION
════════════════════════════════════════════════════════════════════
• Write a 2–3 sentence summary explaining:
  – What this document proposes or requests
  – Why it matters to ordinary people
• Avoid jargon. Assume no prior policy knowledge.

════════════════════════════════════════════════════════════════════
STEP 3: COMMENTING INSTRUCTIONS EXTRACTION
════════════════════════════════════════════════════════════════════
From the docket text, extract and present:
• Deadline(s)
• Required format or questions
• Any explicit areas the agency requests comment on
• Special frameworks referenced (e.g., PRA factors, cost-benefit criteria)
• Open Status: Infer if the comment period is currently open based on the CURRENT DATE and any deadlines found in the text. Return true only if the deadline is in the future.

**SUBMISSION METHOD EXTRACTION (CRITICAL):**
Extract submission method information into three distinct fields:

A) **submissionEmail**: If the agency requests or accepts comments by email, extract the exact email address.
   - If NO email address is found or email submission is not mentioned, set to "NONE"
   - Example: "comments@cbp.dhs.gov" or "NONE"

B) **onlineSubmission**: Set to TRUE if the agency accepts online submission through regulations.gov or any similar federal portal.
   - Most federal dockets accept online submission through regulations.gov
   - Set to FALSE only if the text explicitly states online submission is NOT accepted

C) **submissionMethodsDescription**: Write a clear, user-friendly sentence describing ALL methods the agency accepts for submitting comments.
   - Include ALL methods mentioned: online portal, email, mail, fax, hand delivery, etc.
   - Include specific addresses, emails, or portal URLs if mentioned
   - This text will be displayed directly to users to guide their submission
   - Example: "Comments may be submitted online at regulations.gov, by email to comments@agency.gov, or by mail to 1300 Pennsylvania Avenue NW, Washington, DC 20229."

**DEADLINE EXTRACTION (CRITICAL):**
Extract deadline information into these fields:

D) **deadline**: Human-readable description of the deadline.
   - Example: "60 days from publication" or "February 9, 2026" or "Comments must be received by December 16, 2025"

E) **deadlineDate**: ISO 8601 date of the comment deadline in YYYY-MM-DD format.
   - Calculate the exact date from relative deadlines (e.g., "60 days from publication")
   - Use CURRENT DATE to calculate if the deadline is relative
   - Example: "2025-02-09"
   - Set to empty string "" if no deadline can be determined

F) **responsePeriodDays**: Number of days in the comment period.
   - Extract from phrases like "60-day notice", "30-day comment period", etc.
   - Example: 60, 30, 90
   - Set to 0 if unknown

STEP 4: GENERATE RESPONSE FRAMEWORK (BASED ON NOTICE TYPE)
════════════════════════════════════════════════════════════════════

**IF noticeType = "proposed_rule":**
Generate traditional position-based reason cards.

**CRITICAL: ARGUMENTS-FIRST APPROACH**
For EACH position (support, oppose, mixed), follow this two-step process:

STEP A - Generate Arguments First:
• Brainstorm 10–15 specific, substantive arguments for this position
• Each argument should reference a specific provision, assumption, estimate, or mechanism in the docket
• Draw from these federal evaluation criteria as inspiration:
  1. Problem definition & necessity
  2. Scientific, technical, or economic assumptions
  3. Cost-benefit balance
  4. Distributional impacts
  5. Small entity / vulnerable population impacts
  6. Non-monetizable impacts (privacy, dignity, equity)
  7. Implementation feasibility

STEP B - Cluster Into Categories:
• Group the arguments into 3–5 thematic reason cards
• Each reason card MUST have at least 2 arguments (preferably 3–4)
• If a potential argument would be alone in its category, either:
  – Merge it with a related category, OR
  – Combine it with similar arguments to form a broader theme
• Do NOT create reason cards with only 1 argument
• Rank cards from strongest to weakest impact

Each reason card includes:
- id (e.g., "sup-cost-1", "opp-impl-2")
- topic (short title capturing the theme)
- icon (Material Symbol)
- arguments (array of {id, label, expansion}) — minimum 2 per card

──────────────────────────────────────────────────────────────────

**IF noticeType = "pra_notice":**
Generate PRA factor-based response cards. DO NOT generate support/oppose positions.

**CRITICAL: ARGUMENTS-FIRST APPROACH**
For EACH of the four PRA factors, follow this two-step process:

STEP A - Generate Arguments First:
• Brainstorm 4–8 specific arguments relevant to this PRA factor
• Each argument should reference specific data points, burden estimates, or collection requirements from the docket

STEP B - Cluster Into Categories:
• Group arguments into 2–4 reason cards per factor
• Each reason card MUST have at least 2 arguments
• Do NOT create reason cards with only 1 argument

Generate `praFactors` object with four categories:

1. **necessity** - Whether the collection is necessary
   - Is this information already available elsewhere?
   - Does collecting this serve a legitimate agency function?
   - Could the agency achieve its goals with less information?

2. **burdenAccuracy** - Accuracy of burden estimates
   - Is the estimated time per response realistic?
   - Does the estimate account for record retrieval, compilation, review?
   - Are there hidden costs (software, training, third-party assistance)?

3. **quality** - Enhancing quality, utility, and clarity
   - Will the collected information actually be useful?
   - Are the forms/questions clear and unambiguous?
   - Could the data format be improved?

4. **burdenMinimization** - Minimizing respondent burden
   - Could technology reduce burden (online forms, autofill)?
   - Are there simpler ways to gather this information?
   - Could frequency of collection be reduced?

Each PRA factor category contains reason cards with:
- id (e.g., "pra-nec-1")
- topic (short title)
- icon (Material Symbol)
- arguments (array of {id, label, expansion}) — minimum 2 per card

──────────────────────────────────────────────────────────────────

**IF noticeType = "rfi":**
Generate question-based response cards. DO NOT generate support/oppose positions.

First, extract the specific questions the agency is asking (look for numbered questions, bullet points asking for input, or sections titled "Questions for Comment").

**CRITICAL: ARGUMENTS-FIRST APPROACH**
For EACH question, follow this two-step process:

STEP A - Generate Arguments First:
• Brainstorm 4–8 specific response points for this question
• Each should offer substantive input the agency can act upon

STEP B - Cluster Into Categories:
• Group response points into 2–3 response cards per question
• Each response card MUST have at least 2 arguments
• Do NOT create response cards with only 1 argument

Then generate `rfiQuestions` array where each item represents a question with:
- questionNumber (the original number, or 1, 2, 3 if unnumbered)
- questionText (the agency's actual question, paraphrased if very long)
- responseCards (array of response options for this question)

Each response card has:
- id (e.g., "rfi-q1-1")
- topic (short response angle)
- icon (Material Symbol)
- arguments (array of {id, label, expansion}) — minimum 2 per card

──────────────────────────────────────────────────────────────────

**IF noticeType = "general":**
Generate issue-based response cards without position framing.

**CRITICAL: ARGUMENTS-FIRST APPROACH**
Follow this two-step process:

STEP A - Generate Arguments First:
• Brainstorm 8–12 specific response points relevant to the notice
• Each should offer substantive, actionable input

STEP B - Cluster Into Categories:
• Group arguments into 3–5 issue cards
• Each issue card MUST have at least 2 arguments
• Do NOT create issue cards with only 1 argument

Generate `issueCards` array of general response angles:
- id (e.g., "gen-impl-1")
- topic (the issue being addressed)
- icon (Material Symbol)
- arguments (array of {id, label, expansion}) — minimum 2 per card

════════════════════════════════════════════════════════════════════
STEP 5: REASON CARD STRUCTURE (ALL TYPES)
════════════════════════════════════════════════════════════════════
Every reason/response card, regardless of notice type, must include:

• **Unique ID** (e.g., `sup-cost-1`, `pra-bur-2`, `rfi-q1-1`)

• **Topic** - Short, descriptive, neutral-toned

• **Icon Tag** - Choose ONE Material Symbol:
  shield · lock · timer · lightbulb · verified_user · speed · smartphone · tune · filter_list · policy · gavel · description · trending_up · visibility · groups · balance · warning · calculate · fact_check · edit_document · help_outline

• **Arguments (MINIMUM 2, preferably 3–4 per card)** - Each must:
  – Reference a specific provision, assumption, estimate, or mechanism
  – Explain why it matters legally or practically
  – Be phrased in formal, substantive language
  – NEVER create a card with only 1 argument; merge orphan arguments into related cards

• **Lived-Experience Hook** - 1–2 sentences explaining how someone might credibly support this argument with real-world experience

• **Blind Spots** - What the agency may have underestimated or overlooked
